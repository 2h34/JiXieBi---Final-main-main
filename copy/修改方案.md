> 版本：V1（规划稿，2026-09-10）
> 作用范围：仅 `copy\` 目录内的工程。根目录 `LEFTNOW·`、`RIGHTNOW`、`LEFTNOW· copy`、`RIGHTNOW copy` 一律不动。
> 每个阶段完成后：① Keil 两个目标均编译通过 ② git 提交一次（可回滚） ③ 实机冒烟测试通过后才进入下一阶段。

## 0. 现状基线（已核实）

### 0.1 工程结构
- 两套 Keil 工程（`copy\LEFTNOW·`、`copy\RIGHTNOW`），各约 58 MB / 1694 文件 / 自定义源码约 5,458 行。
- 两个 `f4_show.uvprojx` **MD5 完全一致**——工程文件本身零差异。
- 第三方库（HAL、FreeRTOS、CMSIS）占文件数 95% 以上，自定义代码只有 7 个业务目录：
  `Core / HDL / IRQ / APL / FML / Motor / Mechanism / Task`。

### 0.2 左右两工程的全部实质差异（逐文件 diff 确认，仅 4 处）

| 文件 | 差异 |
|---|---|
| `Core/Src/main.c` | 左板 `solenoid_init(1)` / 右板 `solenoid_init(2U)`；左板 `BlockArm_Init(&DJmotor[0],…)` / 右板 `&DJmotor[1]` |
| `IRQ/Src/CAN_IRQHandler.c` | 左板启用 `Master_message_handler_right`（响应 0x05/0x06/0x08），右板启用 `Master_message_handler_left`（响应 0x03/0x04/0x07）——**当前是交叉对应** |
| `Mechanism/Src/BlockArm.c` | 7 个姿态的 DJI/ZDrive 标定角度左右不同（符号镜像 + 少量 ZDrive 偏置差异） |
| `APL/Inc/myostasks.h` | 仅空行错位，内容一致 |

其余文件（含 TIM_IRQHandler、BlockVacuum、全部 FML/Motor/Task）完全一致。
→ **结论：完全具备"单源码树 + 编译宏区分左右臂"的条件。**

### 0.3 已核实的问题清单

**功能/协议类**
1. 右臂板 FINISH 码不匹配：`myostasks.c` 里 `s_finish_process` 固定用 0x05/0x06/0x08（右臂操作码），但右臂板实际接收 0x03/0x04/0x07。右臂板取块命令（0x03）完成后会回 0x05 的 FINISH，主控按协议等 0x03 回执会失配。代码注释也自相矛盾（注释说存 0x01/0x03/0x04/0x07/0xFF）。
2. 左右臂与信号组的对应是**交叉**的（左板烧录件响应 0x05/06/08，右板烧录件响应 0x03/04/07）。合并时必须原样保留该对应关系，且需要人工最终确认是否本来就是交叉（可能是命名镜像导致）。
3. **潜在 CAN 串扰隐患**：`DJmotor_Func()` 每 2ms 对全部 4 个 DJI 电机槽位发帧，未绑定（Begin=false）的槽位发 0 电流帧。若两块副板挂在同一物理 CAN1 上，每块板会持续给对方那条臂的 DJI 电机发 0 电流帧（= 释放力矩）。需先确认总线拓扑；若同总线必须改为"只对自己绑定的电机发帧"。

**死代码类（已逐个统计全工程引用次数）**
4. `myostasks.c` 的 `flag`、`flag1`~`flag7`：全工程**无任何位置置位**（只有 =0），是调试期遗留的全局触发器，可整体删除（含 myostasks.h 声明）。
5. `MathFunc.c/h` 大组函数无人调用（引用次数 = 定义+声明 2 次）：`PVT_Calculate_*`、`Bezier5_Calculate_*`（4 个）、`buffer_*` 系列（12 个）、`int16_to_bytes`、`int32_to_bytes`、`bytes_to_int16/int32/float`、`uint2float`、`float2uint`、`Lerp`、`normalize_yaw_f`、`cvtFloat2Double`、`Rotate`、`MSG_Byte2Int16/Int32`、`MSG_Int162Byte/Int322Byte/Float2Byte`、`Encode*/Decode*` 宏、`PEAK`、`PeakLimit`、`Trajectory_Planning` 结构体。
   需保留：`ChangeDataByte`（DJmotor.c 用）、`get_s32_from_buffer`、`get_s16_from_buffer`（ZDrive 用）、`N2DEG`、`DEG2RAD/RAD2DEG`、`Clamp/ClampPeak`（DJmotor 用）、基础 typedef（u8/s16 等全工程使用）。
6. `pid.c` 的 2D 向量 PID（`vector2fPIDInit/Reset/Operation`）无外部调用；`Vector.h` + `Vectoc.c`（文件名本身拼写错误）只被 vector2fPID 使用 → 三个文件整体可删。
7. `BlueTooth.c/h`：`Deal_TxPack` 无调用；`Deal_RxPack` 仅被 `UART_IRQHandler` 调用，但 `main.c` 中 `MX_USART1/2_Init()`、`UART_Start_Recieve()` 全部被注释 → **整条 UART/蓝牙链路当前不工作**。
8. `ZdriveSetPVT/ZdriveSetMIT`、`DJmotor_SetVelocityTarget`、`Zdrive_SetVelocityTarget`：公共 API 无调用（可能为将来轨迹/速度模式预留）。
9. `Beep_Alarm()` 无调用者（`BeepAlarmTimes` 仅被它写入）——是报警接口预留。
10. 杂项文件：`MDK-ARM/f4_show.uvguix.glance.before-path-fix.bak`、`MDK-ARM/rebuild_ascii.log`（备份/日志，可删）。

**质量类**
11. `BlockVacuum` 抓取/释放用循环计数计时（400/500 × 5ms 周期 = 2s/2.5s），应改 `HAL_GetTick` 超时，语义不变。
12. 命名不统一：`is_disabled()`/`is_busy()` 无 `BlockArm_` 前缀。
13. 大量注释掉的死代码块：CAN 的 `case 0x05/0x06/CONFIRM_GRAB/STOP`、Pick/Place 的 `MOVE_TO_SAFE` 分支、BlockArm 的 SAFE 特例分支、UART 各回调里的注释行、`"烧录右臂时手动切换注释"` 说明（合并后失效）。
14. 过期 TODO：`BlockArm_SetAutoTarget` 里"TODO: 写入…目标"注释上方实际已填好实测角度。
15. `DOCS/B2通信协议_当前程序实现.md` 与代码已不同步（文档说"只启用左臂处理函数、FINISH 用左臂操作码"，代码相反）。
16. 顶层 `.vscode/c_cpp_properties.json` includePath 写死指向 `RIGHTNOW` 绝对路径。
17. `MOTOR_ZDRIVE_COUNT = 6`：每块板实际只用 1 台 ZDrive（下标 0），`ZdriveFunc` 每 5ms 遍历 6 个 ID 发询帧，CAN2 空耗 5/6 的流量。

**运行时参数（已核实，供参考）**
- TIM2：1 kHz（84MHz/84，Period 1000）。TIM2 中断里：ZDrive 出队每 1ms、DJI 发送每 2ms、ZDriveFunc 每 5ms；TIM3 同频但回调为空（预留）。
- FreeRTOS：tick 1kHz，堆 15,360 B，3 个任务（BlockArmServiceTask 5ms 周期、LedTask、BeepTask）。Led_Water 内部自带 osDelay，无忙等。
- 上电：`DJmotor_Init` 全部槽位 Begin=false、发 0 电流，安全。

**构建环境**
- 已找到 Keil CLI：`C:\Keil_v5\UV4\UV4.exe` → 每个阶段可用命令行 `UV4 -r <uvprojx> -t <target> -o build.log` 自动验证编译。
- `.mxproject` 内为相对路径，文件夹改名对 CubeMX/Keil 安全（uvprojx 内全部相对路径）。

## 2. 阶段一：左右臂合并为单工程（核心，风险最高，优先做）

### 2.1 目录准备
1. `copy` 内 `git init`，提交基线（含两个原工程，作阶段回滚点）。
2. `copy\LEFTNOW·` 改名为 `copy\F4Arm`（去除中间点字符"·"；uvprojx/.mxproject 均为相对路径，改名安全，改完先编译确认）。
3. UV4 CLI 编译 `F4Arm` 单目标，记录基线：build log 无 error、`.map` 的 ROM/RAM/code 大小（存档到 `F4Arm\DOCS\build_baseline.txt`）。

### 2.2 新增 `Config/arm_config.h`
```c
#if defined(ARM_LEFT)
  #define ARM_SOLENOID_CHANNEL   1U     /* 左板吸盘电磁阀通道（现值） */
  #define ARM_DJI_INDEX          0U     /* 左板绑定的 DJI 电机下标（现值） */
  #define ARM_PICK_SIGNAL        0x05U  /* ⚠ 当前左板响应右臂操作码组，保持现行为 */
  #define ARM_PLACE_SIGNAL       0x06U
  #define ARM_RELEASE_SIGNAL     0x08U
#elif defined(ARM_RIGHT)
  #define ARM_SOLENOID_CHANNEL   2U
  #define ARM_DJI_INDEX          1U
  #define ARM_PICK_SIGNAL        0x03U
  #define ARM_PLACE_SIGNAL       0x04U
  #define ARM_RELEASE_SIGNAL     0x07U
#else
  #error "Define ARM_LEFT or ARM_RIGHT in Keil target"
#endif

#define ARM_ZDRIVE_INDEX         0U
typedef struct { float dji_deg; float zdrive_deg; } ArmPose_t;
/* 7 个姿态：LOW_PICK / HIGH_PICK / SECOND_PICK / PLACE_BOTTOM /
   PLACE_LEVEL1 / PLACE_LEVEL2 / SAFE，左右各一套实测值（从两边 BlockArm.c 原样搬入） */
extern const ArmPose_t ARM_POSES[7];
```
（左右姿态表值直接取自当前两边 `BlockArm_SetAutoTarget` 的实测角，含 SAFE 位 20/40 与 -25/40。）

### 2.3 代码改动（逐文件）
| 文件 | 改动 |
|---|---|
| `main.c` | `solenoid_init(ARM_SOLENOID_CHANNEL)`；`BlockArm_Init(&DJmotor[ARM_DJI_INDEX], &Zmotor[ARM_ZDRIVE_INDEX])` |
| `Mechanism/Src/BlockArm.c` | `BlockArm_SetAutoTarget` 的角度改查 `ARM_POSES[]`（switch 结构可保留，数值来自配置表）；同步删过期 TODO 注释 |
| `IRQ/Src/CAN_IRQHandler.c` | ① 两个 handler 合并为一个 `Master_message_handler()`，信号判定改用 `ARM_PICK_SIGNAL` 等宏；② **FINISH 回执改为回显"触发该命令的原始 signal"**（修掉问题 1）：`s_finish_process` 在命令入队时记录实际收到的 signal；③ 删除"手动切换注释"说明与未启用的 handler 残留 |
| `APL/Src/myostasks.c` | `s_finish_process` 赋值改为对应 `ARM_*_SIGNAL`；其余逻辑不动（flag 清理放阶段二） |
| `MDK-ARM/f4_show.uvprojx` | 增加第二个 Target：`f4_show_LEFT`/`f4_show_RIGHT`，各自 Define（ARM_LEFT/ARM_RIGHT）、独立输出目录与 .sct（若需要）；源文件组共用 |

### 2.4 验证
1. UV4 CLI 分别编译两个 target：0 error。
2. 与基线对比 `.map`（左板目标应与原 LEFT 工程 code 大小基本一致，右板同理）。
3. **实机冒烟（用户操作）**，两板各烧新固件：
   - Enable → 归零 → 到 SAFE → 查询 0x00 返回 `[00 01]`
   - 三次取块（1/2/3 连击）、三次放块（底层/一层/二层）+ Release 全流程
   - 确认 FINISH 回执 ID 与主控下发操作码一致（抓包或主控日志）
   - Reset / Disable / 急停
4. 全部通过 → 删除 `copy\LEFTNOW·`（已改名则无此步）、`copy\RIGHTNOW`，git 提交。

**回退预案**：若双 Target 的 uvprojx XML 修改不顺，退化为"同一源码树 + 两个 uvprojx 文件"（复制一份改 TargetName/Define/输出目录），源码层不受影响。

## 5. 阶段四：配置与安全

1. **确认 CAN 总线拓扑（用户答复）**：两块副板是否与主控共挂同一物理 CAN1？
   - 若是：修改 `DJmotor_Func()`，对 `Begin=false` 的槽位**不发帧**（去掉"0 电流填充"广播），消除互发 0 电流的串扰隐患（0.3-3）；同步评估 `ZdriveFunc` 是否需要同样处理（ZDrive 侧已按 ID 过滤，风险低）。
   - 若否：仅记录说明，不改。
2. `MOTOR_ZDRIVE_COUNT` 6 → 1（先确认物理 ZDrive 电机 ID 是否为 1；`Zdrive_IsOurs` 过滤范围随之收窄），CAN2 询帧流量降 5/6。
3. （可选）Keil 优化等级：当前 Target 级 O1、文件级多处 O0 覆盖，**默认不动**，仅记录；如要提 O2 需全量实机回归。
4. （可选，若阶段二确认删蓝牙）CubeMX 关闭 USART1/USART2/DMA 重新生成，删 `usart.c/h`、`dma.c/h` 相关。
5. 验证：两 target 编译 + 电机通信压力测试（连续 10 个取放周期无超时/掉线，观察 CAN 负载）。git 提交。
