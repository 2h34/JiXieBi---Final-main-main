# 通信架构分析：逐条收发 vs 队列化（F4Arm 双固件合并后）

> 目的：评估"把现在的逐条收发改为队列"是否更优。
> 结论先行：**不能一刀切。** 反馈接收绝对不要队列化（最新值语义正确）；
> 真正值得改的只有一处——主控命令接收 `Master_Command` 单值在 5 ms 窗口内的覆盖丢帧。
> 发送侧低频事件无需队列；ZDrive 命令发送**本来就有队列**（CanQueue.c）。

---

## 一、硬件基础（bxCAN 自带缓冲）

STM32F405 的 bxCAN 外设**自带两级硬件缓冲**：

| 方向 | 硬件缓冲 | 深度 | 说明 |
|---|---|---|---|
| 接收 | RX FIFO0 / FIFO1 | 各 3 帧 | 帧到达先入硬件 FIFO，ISR 逐帧取走 |
| 发送 | TX mailbox ×3 | 3 帧 | `HAL_CAN_AddTxMessage` 写入，硬件自动仲裁发送 |

**含义**：硬件层已经有"队列"了。软件要不要再加队列，取决于**生产者/消费者速率是否匹配**，而不是"有队列就高级"。

---

## 二、接收路径现状（两条，均为"最新值覆盖"语义）

### 2.1 DJI 电机反馈（1 kHz 周期帧）

```
CAN1 0x201~0x208 ──► FIFO0 ISR ──► DJmotor_Receive()
     (IRQ\Src\CAN_IRQHandler.c L379-387)
                        └──► DJmotor[i].valNow.*  直接覆盖最新值
```

- 每电机约 1 ms 一帧，每板 1 台 DJI：约 1 kHz 中断率
- 语义：**控制环只需要"最新状态"，历史帧无意义**（位置/速度/电流取当前值即可）

### 2.2 ZDrive 反馈（周期帧）

```
CAN2 ──► FIFO1 ISR ──► ZdriveReceive()
     (IRQ\Src\CAN_IRQHandler.c L417-425)
                        └──► Zmotor[i].valReal.*  直接覆盖最新值
```

语义同上——最新值得反馈。

### 2.3 主控命令（事件帧，唯一低频离散流）

```
CAN1 0x010105xx ──► FIFO1 ISR ──► Master_message_handler()
     (IRQ\Src\CAN_IRQHandler.c L404-416, L207-372)
                        ├── 0x00 状态查询 → 立即回帧
                        ├── 0x01 Enable/Disable → Master_Command = 2/1
                        ├── 0xFF Reset → 清点击 → Master_Command = 3
                        ├── PICK/PLACE → Comm_RecordClick() 点击计数
                        └── RELEASE → Master_Command = 10

任务侧 5 ms 周期消费：
     BlockArmServiceTask() ──► cmd = Master_Command; Master_Command = 0; switch(cmd)
     (APL\Src\myostasks.c L124-128)
```

**这是全工程唯一的"单值逐条"缓冲点**：`volatile uint8_t Master_Command`（CAN_IRQHandler.c L35）。

## 三、发送路径现状（三条）

| 路径 | 现状 | 位置 | 频度 |
|---|---|---|---|
| DJI 电流控制帧 | 直接 `HAL_CAN_AddTxMessage` | DJmotor.c L212-243，TIM2 2 ms 周期 | 500 Hz 固定 |
| ZDrive 命令帧 | **已走 CanQueue 发送队列**（12 深环形缓冲，TIM2 1 kHz 出队） | FML\Src\CanQueue.c L43-98，ZDrive.c L49-94 | 周期轮询，量较大 |
| 主控回执/状态帧 | 直接 `HAL_CAN_AddTxMessage` | CAN_IRQHandler.c L42-98，isr 与任务上下文 | 低频事件 |

> 注意：ZDrive 命令帧**已经队列化了**（`ZdriveEnqueue` → `CAN_Enqueue` → TIM2 中断 `ZdriveDequeue` 出队）。
> 这说明原作者对"高频周期发送"选择队列、对"低频事件发送"选择直发——架构判断是清醒的。

## 四、分场景评估："改队列"到底值不值

| 流 | 队列化的收益 | 结论 |
|---|---|---|
| DJI 反馈接收 | **负收益**：增加处理延迟、占用内存，控制环反而变差 | ❌ 不改（正确语义：最新值） |
| ZDrive 反馈接收 | **负收益**，同上 | ❌ 不改 |
| DJI 电流帧发送 | **零收益**：固定 2 ms 节奏，直发无抖动，加队反而引入延迟抖动 | ❌ 不改 |
| ZDrive 命令帧发送 | 已队列化，无需再动 | ✅ 已是最优 |
| 主控回执/状态帧发送 | **低收益**：低频事件 + 3 个 TX mailbox 足够；唯一隐患是发送失败未重试 | ⚠️ 可选（见 §6.2） |
| **主控命令接收** | **中高收益**：消除 5 ms 窗口内"命令 A 被命令 B 覆盖"的丢帧 | ✅ **唯一建议改的点**（见 §5） |

## 五、唯一建议：主控命令接收加 FIFO（消除覆盖丢帧）

### 5.1 现状缺陷（真实现场会踩到）

`Master_Command` 是单字节 volatile，ISR 写、5 ms 任务读后清零（myostasks.c L124-128）。

**丢帧窗口**：若在任务读走的 5 ms 窗口内连续到达两条**不同**命令（例如主控急停后立刻复位），
后到的覆盖先到的，先到的命令**静默丢失**：

```
时刻 0ms    ISR: Master_Command = Master_Enable   ← 被覆盖
时刻 2ms    ISR: Master_Command = Master_Reset    ← 覆盖 Enable
时刻 5ms    任务: 读到 Reset，Enable 永远丢失
```

比赛中"急停 → 立刻复位"连发、或主控程序化快速发多条命令时，这是真实风险。

### 5.2 方案：ISR 入队、任务出队的命令 FIFO

```
ISR (Master_message_handler) ──► Comm_Enqueue(cmd)     生产者（中断）
                                         │
                                   命令 FIFO（8 深）
                                         │
任务 (BlockArmServiceTask 5ms) ──► 有命令？→ 取一条执行   消费者
```

- 深度 8 足够：命令是离散事件，比赛节奏下 5 ms 窗口内最多 1~2 条
- 实现两选一：
  - **FreeRTOS 消息队列**（`osMessageQueueNew`）：现成、支持 ISR 安全 `osMessageQueuePutFromISR`；堆 15360 字节够用
  - **环形数组 FIFO + 临界区**（复用 CanQueue 的环形思路，8 深 uint8_t）：零动态内存、更适合 ISR；需要 `__disable_irq`/`__enable_irq` 保护（本工程已有此用法：CAN_IRQHandler.c L149/L161）

### 5.3 ⚠️ 必须保留的既有语义：点击计数（不能简单排队）

PICK / PLACE 命令目前走**点击计数**（CAN_IRQHandler.c L110-131：同信号 1 秒内 1/2/3 次点击
分别映射 LowPick / HighPick / SecondPick …），由任务侧 `Comm_ClickProcess()`（L134-203）
在 CLICK_GAP_MS = 1000 ms 超时后转成一条命令写入 `Master_Command`。

**改造时这条链路不动**：点击计数仍由 `Comm_ClickProcess()` 聚合，聚合出的**最终命令**再入 FIFO
（而不是把每次点击都入队）。否则"连按 3 次"会被当成 3 条独立命令执行 3 次。

### 5.4 预期改动面（约 3 个文件、不到 60 行）

| 文件 | 改动 |
|---|---|
| `IRQ\Src\CAN_IRQHandler.c` | 新增命令 FIFO 及 `Comm_Enqueue/Comm_Dequeue`；`Master_message_handler` 与 `Comm_ClickProcess` 终点改为入队 |
| `APL\Src\myostasks.c` | `BlockArmServiceTask` 改从 FIFO 取命令执行（保留读完即清语义） |
| `IRQ\Inc\CAN_IRQHandler.h` | 暴露 2 个 Comm 接口 |

风险低：不涉及电机/机构代码，纯命令通路替换；改完双 Target 编译 + 实机命令连发验证。

## 六、两个附带观察（可选，非本次重点）

### 6.1 回执发送失败未检查
`Master_message_handler` 内 L242/L260/L274 的 `HAL_CAN_AddTxMessage` 均未检查返回值；
若 3 个 TX mailbox 恰好占满（概率低），回执静默丢失、主控会以为没收到。
可改为失败重试或复用 ZDrive 的发送队列。

### 6.2 回执发送优化优先级低
主控回执是低频事件，最多同时 1~2 条，3 个 mailbox 足够。真正高频的 ZDrive 命令
**已经在队列里**。此条可延后。

---

## 七、一句话结论

- ❌ 反馈收发（DJI / ZDrive）：保持 ISR 直读最新值，**不要队列化**
- ❌ 低频回执 / 固定周期电流帧：直发即可，**不要队列化**
- ✅ **唯一建议**：主控命令接收把 `volatile Master_Command` 换成 8 深命令 FIFO，
  消除 5 ms 窗口覆盖丢帧；**点击计数语义保留**，聚合后的命令才入队
- ℹ️ 工程已有的 CanQueue.c 是"发送队列"，与本次讨论的"接收命令队列"是两回事，不要混用
